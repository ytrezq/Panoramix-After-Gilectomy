## The high findings

- **c00069** `execute((address,address,uint256),bytes[],bytes32) (and executeWithPermit, fallback: 7 copies of the SELECT loop)` semantics (src__chains__RobinHood__TakerSubmitted.sol:RobinHoodSettler): The bytecode reads GAS once, before the CALL (pc 0x4787), and the test after the call compares the threshold with that stacked value (pc 0x47e8 dup14 gt). The text prints `gas_remaining` again in the post-call test, which reads as a fresh gas read after the call, i.e. a different, smaller value. *Rule:* Environment reads whose value changes during execution (GAS, RETURNDATASIZE, MSIZE, BALANCE, SLOAD/TLOAD after a write) must not be duplicated or moved past a CALL or any other gas-consuming instruction; when such a value is used at more than one point, bind it to a named temporary at the read. *Verified:* disassembly: 0x4786 eq, 0x4787 gas, ... 0x47d2-0x47d4 xor mul xor, call; 0x47e3 jumpdest, 0x47e7 jumpi (success->break), 0x47e8 dup14, 0x47e9 gt, 0x47ea or -> no second GAS
- **c00122** `setRewardTokenAddresses(address[])` semantics (contracts__strategies__NativeStaking__CompoundingStakingStrategy.sol:CompoundingStakingStrategy): The event has two dynamic arrays; the text prints the second head word (the offset 32 * oldLength + 96) as the value of _newAddresses and appends the new array's length and elements to the first Array, so read literally the event's second argument is a number and its first argument is not the old address list. *Rule:* When decoding log data against a signature with several dynamic parameters, read every head word as an offset into the data, decode each parameter at its own offset, and never print an offset as a parameter value. *Verified:* reading only (data layout worked out from the stores: mem[128] = 64, mem[160] = 32 * L_old + 96, mem[192] = L_old, old at 224, L_new and new after)
- **c00171** `handleOps((address,uint256,bytes,bytes,uint256,uint256,uint256,uint256,uint256,bytes,bytes)[],address) (also handleAggregatedOps 3603-3604, simulateHandleOp-like unknownd6383f94 1670-1672)` semantics (contracts__core__EntryPoint.sol:EntryPoint): The bytecode reads `preGas` (GAS at pc 0x1ad6) before the innerHandleOp CALL (pc 0x1b14), but the text binds it as `_3 = gas_remaining` after the call, next to `_5`, so `_3 - _5` reads as ~0 instead of the gas used by the inner call; the later single gasleft() of _handlePostOp is re-printed inline six times, across the deposit SSTORE and the LOG. Read literally, actualGas, actualGasCost, the refund credited to the deposit and the event data are all wrong. *Rule:* A GAS read is not a pure expression: bind each GAS opcode's result to a variable at the exact point where it executes (before any later CALL, SSTORE or LOG) and refer to that variable at every use; never sink or duplicate it. *Verified:* disassembly: 0x1ad6 gas (preGas), call encoding with selector 0xeb993ab<<0xe1 = 0x1d732756, 0x1b12 address, 0x1b13 gas, 0x1b14 call, 0x1b2d push4 0xdeaddead; the text has no GAS binding before its call at line 2600
- **c00384** `multicall((address,uint256,bytes)[])` semantics (contracts__lens__UniswapInterfaceMulticall.sol:UniswapInterfaceMulticall): The GAS read that gives gasLeftBefore is executed inside the loop, right before each call (disassembly: GAS at 0x158 after the loads of calls[i], GAS at 0x1c1 after the call, then SUB), but the text hoists it to the first line of the function (_1 = gas_remaining, even before the calldata checks). The text therefore reports, for every call i, the gas used since the function entry instead of the gas used by call i. *Rule:* GAS is not a pure expression: its value changes with every instruction, so a GAS read must never be hoisted, merged (CSE) or moved across other instructions, in particular out of a loop or across a call; bind each read to a fresh variable at its own position. *Verified:* pancxx disasm (GAS opcodes only at 0x158 and 0x1c1, both in the loop body); the execution checks do not catch it because gas-dependent outputs are not compared
- **c00432** `calculatePaymentAmountNativeExternal (unknown67a88db0), calculatePaymentAmountLinkExternal (unknownc07d3658); also fulfillRandomWords (unknown301f42e9)` semantics (src__v0.8__vrf__dev__testhelpers__ExposedVRFCoordinatorV2_5_Arbitrum.sol:ExposedVRFCoordinatorV2_5_Arbitrum): The bytecode reads GAS once (pc 0x48c3, before the SLOAD of slot 12) and reuses it, but the text prints a bare gas_remaining in five lines of each payment function, after the L1GasFee log and in the return value, so read literally each one is a later, smaller gas reading. The same happens with the single 'g := gas()' of _callWithExactGas (1729) and the payment of fulfillRandomWords (1787-1845), which c00433's review did not mention. *Rule:* GAS is not a pure expression: bind each GAS result to a variable where the instruction executes (as the text already does with '_3 = gas_remaining' at the entry of fulfillRandomWords) and use the variable at every later use. *Verified:* disassembly (pancxx disasm): one GAS at 0x48c3 in the shared payment code; reading for the rest
- **c00460** `_fallback (receive), depositTransaction(address,uint256,uint64,bool,bytes)` semantics (src__L1__OptimismPortal2.sol:OptimismPortal2): The gas-burning loop is missing: the text tests 'initialGas - gasleft() >= amount' once and otherwise falls through to 'revert with Panic(17)', while the bytecode loops (back edge 0x3859 -> 0x383b, ++i checked) until enough gas is burned and then returns normally; a deposit whose gas limit costs more than the gas already used is shown as reverting. *Rule:* GAS is not loop-invariant: a loop whose condition reads GAS (directly or through a value computed from it inside the loop) must stay a loop, e.g. 'while initialGas - gas_remaining < amount: i = i + 1'; never conclude 'condition invariant, so the loop only exits by overflow of i' when the condition contains GAS. *Verified:* disassembly 0x3834-0x3861 (gas at 0x383d re-read each iteration, jump back at 0x3859); text_check run --per-selector 32: 0 differences because no sampled call takes the burn path
- **c00465** `fulfillRandomWords(...)` semantics (src__v0.8__vrf__VRFCoordinatorV2.sol:VRFCoordinatorV2): The bytecode reads GAS three times outside calls: startGas at the entry (0x2830), the exact-gas check (0x3df6) and gasleft() in the payment (0x3ed2). The text binds only the last one (_487) and prints the entry read as a bare gas_remaining inside the payment formula, so 'SafeMath.sub(gas_remaining + stor11_88, _487)' reads as current gas minus current gas, and the same name gas_remaining also denotes the exact-gas check's read at 1538. *Rule:* GAS is not a pure expression: bind each GAS read to a fresh variable at its own position (_startGas = gas_remaining at the entry) and never let a later expression refer to an earlier read by the bare name. *Verified:* pancxx disasm (non-call GAS reads at 0x2830, 0x3df6, 0x3ed2); same root cause as c00384
- **c00499** `setKeepers(address[],address[])` semantics (src__v0.8__automation__v1_2__KeeperRegistry1_2.sol:KeeperRegistry1_2): Same log-decoding error as c00122: the second dynamic array is printed as its offset (32 * keepers.length + 96) and the first Array swallows the payees' length and elements, so read literally the event's payees argument is a number. *Rule:* Decode each dynamic event parameter at the offset given by its head word; never print a head word of a dynamic parameter as its value. *Verified:* reading only (stores: mem[128] = 64, mem[160] = 32 * n + 96, keepers at 224, payees after)
- **c00499** `performUpkeep(uint256,bytes)` semantics (src__v0.8__automation__v1_2__KeeperRegistry1_2.sol:KeeperRegistry1_2): gasleft() after the call is read once, but the text prints a bare gas_remaining in every later line (overflow tests, two balance writes, the keeper balance write, the event), after SSTOREs, so read literally each is a new and smaller gas value; the exact-gas test likewise prints its single GAS read twice. The entry read is correctly bound as _3. *Rule:* Bind each GAS result to a variable where it executes and use the variable afterwards (as done for _3). *Verified:* reading only (same known GAS-binding issue as c00432, c00465)
- **c00549** `execute, executeWithPermit, fallback (Select.select inlined: SELECT action, also nested under executeSelected)` semantics (src__chains__Mainnet__TakerSubmitted.sol:MainnetSettler): The bytecode reads GAS once before the CALL (0x543b, beforeGas) and compares that stacked value with the threshold after the call fails (0x549c dup14 gt). The text prints the comparison as '> gas_remaining' after the call, so it reads as the gas left after the failed trial, which is smaller: a trial that burns its whole gasCap would, by the text, revert the transaction instead of trying the next candidate. *Rule:* GAS is not a pure value: when a GAS result is used after any later instruction that consumes gas observably (CALL, another GAS read on another path, a loop back-edge), bind it to a variable at its read point (beforeGas = gas_remaining) and print that variable at each use; print gas_remaining only where the read itself happens. *Verified:* pancxx disasm: single GAS at 0x543b before CALL at 0x5489; failure path 0x5497-0x549f compares dup14 (that GAS) with the threshold
