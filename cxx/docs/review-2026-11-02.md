# 01-core1 — core/base, smallvec, sync, errors, platform, platform_posix, memo, watchdog, jobs, budget

### F1 [severity: low (latent; medium if any thread re-attaches after its Watch exists)] budget.cpp:67 / budget.cpp:84 - attach_thread() can overwrite the watchdog's EXPIRED_MARK: the Timeout is lost for good
Checked: the present callers (output/ast.cpp:79-83, driver/pipeline.cpp:438-442 and :566-570) do `Attach attach(budget)` BEFORE `watch.emplace`,
and output/contract.cpp:388 attaches a budget with no Watch, so today the window is not exercised; driver/decompile.cpp:90 not checked.
`attach_thread()` does `if (!expired()) guard_.low.store(mark)`: a check-then-store, not atomic against `expire()` (watchdog thread: `expired=true; low=MAX`).
Sequence: attach reads expired==false; watchdog runs expire() (sets expired, low=MAX); attach stores low=mark. `check_stack()` compares SP only
against `low`, and `Watchdog::run()` calls expire() once per Watch (`fired_`), so nothing ever raises the mark again: the job runs with no time
limit (only memory/depth caps). Trigger: a Watch whose deadline is already past (PANORAMIX_TIMEOUT tiny, or a long loader stage) and a thread that
(re)attaches the budget after the Watch exists (output/contract.cpp:389, output/ast.cpp:28 attach per thread/phase; whether a Watch is live at
those points is to be checked by the owner of those files). Fix: store then re-check: `guard_.low.store(mark); if (expired()) guard_.low.store(EXPIRED_MARK);`
or a CAS that never replaces EXPIRED_MARK.

### F2 [severity: medium] memo.hpp:237 - a memo whose first growth happens with no charger is never charged, for its whole life
`grow()` picks the charger only at the first growth (`cap_ ? charged_ : (bound_ ? bound_ : tl_mem_charge)`); when that is nullptr (no ContextScope /
MemChargeScope active, tl_mem_charge == nullptr) `charged_` stays nullptr and every later growth (x2, x4) is uncounted: a hostile contract that fills
such a memo defeats PANORAMIX_MAX_MEMORY (rule 8) until the system's malloc fails. Is there a memo filled before the ContextScope is installed (a
module state made at context construction, a static/global memo)? If not, it is only a trap. Fix: re-resolve `c` when `charged_` is null (charge the
whole new table then), or assert `c != nullptr` in debug.

### F3 [severity: low] memo.hpp:187 - a NIL key (raw()==0) in release makes a phantom entry on every call: unbounded count_ and growth
`slot()` only `assert`s `!key_empty(k)`; in release a key whose first word is 0 is written into an "empty" slot (`s.key = k` keeps it empty), `count_`
is incremented, the entry is never found again, and each call repeats it: `count_` climbs, `(count_+1)*2 > cap_` grows the table without bound
(bounded only by the budget, F2 aside). Is any memo keyed by a Value that can be NIL/None (Key2/Key3 with a NIL first component)? Fix: handle
key_empty(k) explicitly (a dedicated flag slot, or throw InternalError), not an assert.

### F4 [severity: low] smallvec.hpp:89 / :76 - grow()/resize() have no size-overflow check: `cap * sizeof(T)` wraps for a huge n
`resize(n)` and `append(s)` pass caller sizes straight to `grow(need)`; `cap * sizeof(T)` wraps when need >= 2^64/sizeof(T), malloc gets a small
block, `memcpy`/`memset` write past it and `n_ = n` makes `end()` wild. Reachable only if a caller passes an unchecked EVM length (a 256-bit length
truncated to usize) to resize/append; the caps (MAX_ZEROES_SIZE, MAX_CODECOPY_SIZE) suggest they are checked upstream — a question for the callers.
Fix: `if (need > SIZE_MAX / sizeof(T) / 2) throw SizeLimit(...)` in grow(). Also: malloc gives max_align_t alignment only; a T with alignas(32) would
be misaligned on the heap while fine inline (static_assert alignof(T) <= alignof(std::max_align_t) as memo.hpp does).

### F5 [severity: low] budget.cpp:54 - ~Budget() of a budget that is not the top of the thread's chain leaves a dangling prev_ in the chain
`~Budget()` detaches only when `tl_budget == this`. A nested budget destroyed out of order (B attached over A, A destroyed first) stays as B's
`prev_`; B's `detach_thread()` then sets `tl_budget = &A` (freed) and `tl_guard = &A.guard_`: the next `check_stack()` reads freed memory, and
`Budget::current()` returns a dangling pointer. RAII scoping normally prevents it; the Attach helpers (driver/internal.hpp:41, output/ast.cpp:28)
are to be checked for a budget whose lifetime is shorter than its nesting. Fix: in ~Budget walk the chain and unlink `this` wherever it is (or assert).

### F6 [severity: low] platform_posix.cpp:49-77 - the default thread attributes are process-wide: a host thread creating a thread in the window gets a 64 MiB stack
`spawn` sets `pthread_setattr_default_np` for the length of a `std::thread` creation under `spawn_lock`; the lock covers only our spawns. In the python
module, any host thread (python's own threading, a C extension) creating a thread meanwhile inherits WORKER_STACK (64 MiB of address space, and the
blocked-signal mask is per-thread so that part is fine). Also the SpinLock (sync.hpp:12, "a few instructions") is held across mmap + clone of a
64 MiB stack: on the 2-CPU machine concurrent parallel_for callers spin. Not a correctness bug for the decompiler itself; worth a note in the
header's contract. Fix: `pthread_attr_setstacksize` on a per-thread attr with `pthread_create` here (POSIX is allowed in *_posix.cpp), wrapping
the native handle, instead of the process default; or at least `std::this_thread::yield()` in the SpinLock's inner loop.

### F7 [severity: low] budget.hpp:97-98 - the hot-path TLS (tl_guard, tl_budget) is not declared PAN_TLS (initial-exec)
base.hpp:16 asks the hot paths' thread_locals to use PAN_TLS; `check_stack()` ("one compare on the hot path", at the entry of every recursive
function) reads `detail::tl_guard` declared `inline constinit thread_local` without it. In the dlopen'ed python module the default model is
global-dynamic: a `__tls_get_addr` call per check_stack()/poll(). Same for memo.hpp:38 `tl_mem_charge`. Performance only (-fweb/-Ofast builds).
Fix: add PAN_TLS to the three declarations.

### F8 [severity: low] watchdog.cpp:88-96 - after_fork_child placement-news a std::mutex / condition_variable that may be locked, without destroying them
Formally UB (the objects' lifetimes are ended by overwriting); it is the usual fork idiom and works with glibc's trivially-initialized pthread
types; the registration of the handler is tied to `instance()`, so a Watchdog never used before the fork registers nothing (fine). Note only:
the parent's Watches in the child (generation check in remove(), watchdog.cpp:60) are handled correctly. No change needed unless musl/other
libc differ; a `static_assert(std::is_trivially_destructible_v<...>)`-style note would document the assumption.

No finding in: base.hpp, sync.hpp, errors.hpp (note: `MemoryLimit()` allocates a std::string + shared_ptr while out of memory and may surface

### F1 [severity: medium] /home/claude/wt-cxx/cxx/src/core/evmint.cpp:292 - EvmInt::mask: the `size + off < 63` fast-path test wraps in u64, then shifts an i64 by >= 64 (UB)
`mask(size, off)` tests `size + off < 63` and then computes `((i64(1) << size) - 1) << off`. Both operands are u64 taken
from contract numbers (shift / mask widths); when `off` is close to 2^64 (e.g. off = 2^64 - 1, size = 1: the sum wraps to 0)
or `size` is (size = 2^64 - 5, off = 10: sum 5) the test passes and the shift amount is >= 64 -> undefined behaviour
(with -Ofast the compiler may assume it never happens). The `check_bits()` calls that would have thrown SizeLimit come
only after the fast path. Fix: `if (size < 63 && off < 63 - size)` (or check_bits on both first, then the fast path).

### F3 [severity: low] /home/claude/wt-cxx/cxx/src/core/context.cpp:287 - HashCons::seq / bigint / bytes call reserve_one() before the lookup: a hit can throw MemoryLimit and grow the table one insert too early

## 03-evm

# 03-evm: cxx/src/evm/, tools/gen_grammar.py, spec/evm.def (2 Nov 2026)

Overall: the slice is small, linear and clean. The bitmaps (insn_start / jumpdest / static_dest) are
sized to the code, `Bitset::test` is false past the end for any u64, `static_dest.set` is guarded by
`target < n`, a 0x5b inside a push's immediate is never a jumpdest (the push's `any{n}` states are
distinct from the start state), a push the end cuts is handed over with `imm_len < imm_size` and
`push_word`/`push_u64`/`append_hex_be` zero-fill the missing low bytes as the EVM does. `small_value`
and `push_u64` check before shifting (no u64 overflow). The metadata machine bounds every string
length against `pe` before `fexec`. No recursion, no floats, no pthread, no hand-written parser (the
only non-Ragel walk, `sets_free_memory_pointer`, is a bounded stack simulation over `for_each_insn`,
not a parser). No shared state: every pass is a pure function of its span.

### F1 [severity: medium] cxx/src/evm/exec_ref.rl:48-56 - `start` is never checked against the size: `start > size` is an out-of-bounds read
`exec_block_ref` sets `p = code + start`, `pe = code + size` and runs `write exec` with no guard
(`check_code_size` only bounds `bytes`). Ragel's exec loop tests `p == pe`, never `p < pe`: with
`start > size`, `p` starts past the buffer and the machine reads bytes until it happens to break or
crash; `cs != start` afterwards also makes it hand a bogus "cut push" built from `*ib` past the end.
Trigger: any caller passing a stack word as `start` without first testing `is_jumpdest` (the VM of
lot 5 "copies this skeleton"; the comment documents the precondition but nothing enforces it).
Fix: `if (start > size) throw` (or return `FellOff{size,size}`) before `write init`; and a
`start == size || is_insn_start(start)` assert in debug.

### F2 [severity: low] cxx/src/evm/decoder.hpp:109-116,195 - with `kMaxCodeSize = 0xffffffff`, `Insn::next_pc()` wraps in u32 for a cut push near the end
`check_code_size` accepts `size == 0xffffffff`; `next_pc()` is `pc + 1 + imm_size` (u32): a PUSH32
the end cuts at `pc = 0xfffffffe` gives `next_pc() = 0x1f`, and the same sum is the one
`analyse` (`n - last < 1u + kImm[...]`) and `BlockEnd::next` are documented from. Only reachable
through the python module (the CLI caps at 128 MiB), so low. Fix: `kMaxCodeSize = 0xffffffff - 33`
(so that `pc + 1 + 32` fits) or make `next_pc()` return u64 / clamp to `size`.

### F3 [severity: low] cxx/src/evm/decoder.cpp:101-107 - `CodeMap::insn_at(pc)` with `pc >= size` reads out of bounds and underflows `rest`
`code[pc]` is unchecked and `rest = code.size() - pc - 1` wraps (usize) when `pc >= size`, so
`imm_len = imm_size` with `imm` pointing past the code. Both callers in the slice (text.cpp:149,
194) pass pcs the analysis produced (`cut_push`, an idiom's `first_pc`), so no trigger today; the
precondition is only a comment. Fix: `[[assume]]`/assert `pc < code.size()`, or return a 0-length
Insn past the end as `Bitset::test` is false past the end.

### F4 [severity: low] cxx/src/evm/metadata.rl:33 - a solc version of 3 bytes is kept from any bstr key, a tstr "solc" of 3 bytes too
`skip` records `md.version` whenever `key == Key::Solc && len == 3`, for `bstr` and `tstr` alike
(both share `@skip`); solc writes the version as a bstr, a prerelease as a text. A 3-char text
("1.0") would be reported as a binary version. Cosmetic: the `lang` verdict is unaffected. Fix:
a separate `@skip_bstr` action for the bstr branch, or a `bool text` set by the tstr heads.

### F5 [severity: low] cxx/src/evm/text.cpp:181,188 - `kFarTarget` is also the value of a real target 0xffffffff
`small_value` returns `kFarTarget` for `v >= 0xffffffff`, so a push of exactly 0xffffffff before
a JUMP is indistinguishable from a 2^32+ target. Harmless now (a pc of 0xffffffff is never
`< size`, so both are "no jumpdest" and `Idiom::target` is only compared with jumpdests), noted

`kFarTarget`, or `v > kFarTarget` with `static_dest.set` kept behind `target < n`.

Nothing found on: the action ordering within a byte (every analysis action reads only `p` and
bits below `p`, as the header requires; `before()` = `prev(pc)` excludes `pc` itself); the union
`(insn >begin | static_jump | static_jumpi | selector)* | (fmp? . any*)` (the idioms are whole
instructions, so their alternatives start and end on instruction boundaries); `bad_static_jumps`

Hostile input: all passes are O(size) with no allocation beyond 3 bits/byte + the idioms vector

# 04-algebra1: cxx/src/algebra/{construct,masks,eval}.{hpp,cpp} - 2 Nov 2026

Focus: soundness of the rewrites mod 2^256, the masks' shifts, signed ops, eval vs the EVM.
The word-level rewrites I checked line by line are sound (add/mul term normal form incl. eff_size,
merge_group, mask-of-mask, mask of MUL(2^p), ADD residue mod 2^hi, SIGNEXTEND, DIV/SDIV/MOD/SMOD/EXP

### F1 [severity: high] masks.cpp:223-238 - max_bits of a MASK_SHL of a wide value is wrong, and construct turns such masks into 0
max_bits_of(MASK_SHL) assumes the operand is a word: `off >= 256 -> return 0`, and `top = off + size`
clipped to max_bits(x) = 256 then `+= shl`. For x with may_be_wide(x) (DATA, MEM of >32 bytes...) the
bits past 256 exist and mask_concrete() (construct.cpp:524-549) deliberately keeps such fields as
given, so MASK_SHL(8, 256, -256, DATA) (the 33rd byte moved to bit 0) is a legitimate node whose
max_bits is reported as 0, and MASK_SHL(64, 224, -224, DATA) (bits [224,288)) as 32 instead of 64.
Consumers then rewrite unsoundly: mask_rules (construct.cpp:437-438) `mb <= o -> small(0)`, so
AND(0xff, MASK_SHL(8, 256, -256, DATA)) becomes the constant 0; signextend (construct.cpp:874)
`max_bits(x) < bits -> x` drops the extension; sar (851) becomes shr; is_bool (1053) may call it a bool.
Fix: in max_bits_of(MASK_SHL) return 256 when v.size() == 4 && may_be_wide(v[3]) (before the field
arithmetic); same guard in mask_rules before using mb on an x that is itself a mask of a wide value.

### F2 [severity: medium] masks.cpp:130-152 / eval.cpp:272 - may_be_wide stops at one MASK_SHL level: a mask of a wide value whose field is not moved below bit 256 is still wide, but is evaluated as a word
may_be_wide(MASK_SHL(...)) is false (default). Evaluator::run only checks the direct operand
(`op == MASK_SHL && may_be_wide(v[3])`): for MASK_SHL(8, 0, 0, MASK_SHL(64, 256, 0, DATA)) the inner
node goes to the env, the outer is "pure" and is computed by mask_shl_word on the inner's Word256,
which cannot hold the inner's bits [256,320): the result is 0 whatever the env says. The same
single-level test is in field_of_mask (construct.cpp:110) and push_term (214): the inner wide mask
becomes a plain word term `Acc{t, k, 0, 256}` in sums. Triggers with any mask of a wide value whose
off + size + shl > 256 (memory copies, sha3 of >32 bytes). Fix: may_be_wide returns true for a
MASK_SHL whose x is wide and whose concrete off + size + shl > 256 (or whose fields are symbolic).

### F3 [severity: low] construct.cpp:122-163 - the distribution of products of sums is bounded per call only, not in total; no poll()/check_stack() in push_product/push_term
kMaxExpansion = 64 bounds one level of distribution; each distributed factor t is pushed again with
push_product(depth + 1) which may distribute again. Only push_term checks `depth > 64` (SizeLimit),
and poll() is first called in add_terms, after the whole expansion. A nested MUL(ADD(MUL(ADD(...))))
of depth ~32 made with mk() (loader / a non-normalized tree, since the constructors' outputs are
normal forms whose sums exceed 8 terms quickly) does up to 4^32 push_term calls before any poll.
Is this reachable from the trace loader? If so: count the expansions across the recursion (a budget
in the Acc vector's size, e.g. throw SizeLimit past limits::MAX_NODE_COUNT terms) and poll() per level.

### F4 [severity: low] eval.cpp:131-199 - eval_op indexes a[0]..a[3] on the strength of OpInfo arity_min only (question)
`a[0]` for ADD/MUL/AND/OR/MAX/MIN and `a[3]` for MASK_SHL are read after the arity_min check; if any
of these ops has arity_min below the index used (e.g. ADD/MAX with arity_min 0 or 1, MASK_SHL < 4)
an empty or short span (construct.cpp:49 fold() builds it from the caller's args) reads out of
